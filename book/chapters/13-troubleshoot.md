# 第 13 章　用证据定位问题

排查问题的起点，是把“不能用”改写成一句可以核对的话：在什么版本、哪个目录，用什么输入执行哪条命令，实际出现什么，与期望差在哪里。先保留第一条有意义的错误，再决定下一步。末尾的“构建失败”只是结果，前面缺少的工具名或失败的断言通常更有用。

本章沿用一个固定顺序：**输入与现象 → 假设 → 最小验证 → 结果解读**。假设可以被推翻；最小验证的价值，是每次只改变一个相关条件。以下错误是教学场景，不表示编写本书时在当前机器上发生过。命令的目录与预期结果均写在案例中。

## 案例一：还没编译就提示找不到清单

输入与现象：你在仓库根输入上一章的小包测试命令，终端提示找不到 Cargo.toml。直觉可能是“包不见了”，但这条错误发生在选择构建目标之前。

假设：你站在仓库根，而 Rust 工作区在 codex-rs。先不重新安装 Rust，也不删除缓存。在仓库根执行：

```bash
pwd
rg --files -g Cargo.toml codex-rs/ansi-escape
```

预期第一条显示当前目录，第二条找到小包清单。若系统没有 rg，可在文件管理器中查看同一路径。它们只能证明目录位置与文件存在，尚未证明清单有效或依赖可以下载。

最小验证：继续在仓库根执行显式指定清单的命令：

```bash
cargo +1.99.1 test --manifest-path codex-rs/Cargo.toml -p codex-ansi-escape --lib
```

预期不再出现“从当前目录找不到 Cargo.toml”这一类错误，并继续准备依赖、编译或运行测试。这里显式选择固定工具链，因为指定清单路径不会让 rustup 按子目录自动选择版本。若出现网络错误，说明已经越过了最初的路径问题；新错误应单独记录。若目标包名找不到，再核对包清单的 name，而不是根据目录名猜测。

结果解读：可以确认“目录问题已解决”，却不能提前写“测试通过”。路径、依赖获取、编译、测试是连续阶段，一个阶段的证据不能替代后一个阶段。下次也可以先进入 codex-rs 再执行 Cargo 命令，两种方式选择一种即可。

## 案例二：just 存在，测试仍然启动不了

输入与现象：在仓库根执行小包的 `just test` 配方，收到 Cargo 没有 nextest 子命令的提示。看到配方名里有 test，并不意味着测试已经开始。

假设：just 只是启动了配方，真正执行测试的 nextest 尚未安装。在仓库根先查看配方：

```bash
just --show test
```

预期显示 test 配方及其中的 `cargo nextest run`，它不会因为展示配方而运行测试。如果连 just 自身也找不到，问题应先停在 just 的安装或 PATH 上，不能把两个缺失混成一个原因。

然后进入 codex-rs 目录执行：

```bash
cargo nextest --version
```

预期成功显示版本，或者再次确认子命令不存在。后者支持假设。安装文档给出的修复是在该目录运行：

```bash
cargo install --locked cargo-nextest
```

预期完成工具安装；安装过程中可能下载依赖和编译工具。安装后重新检查版本，再回到原先的小范围测试。也可以暂时直接运行第 11 章的 Cargo 库测试，以区分“测试执行器缺失”和“库代码失败”。

结果解读：辅助工具装好，只证明执行入口可用。若随后出现断言失败，应记录新的失败输入。不要为了让入口可用就扩大到全仓测试，也不需要添加所有特性；这些改变不会自动补上缺失的 nextest。

## 案例三：后半段文本为什么消失了

输入与现象：某处向 `ansi_escape_line` 传入带颜色的首行加换行和尾部文字，却只拿到首行。你预期完整显示，于是怀疑 ANSI 解析器丢内容。

假设一是解析器错误，假设二是调用了只接收单行内容的接口。先阅读契约。在仓库根执行：

```bash
rg -n 'pub fn ansi_escape_line|expected a single line|multiline_warning' codex-rs/ansi-escape/src
```

预期找到函数、警告消息与相关测试。函数上方的说明明确写着：多行输入会记录警告并返回第一行。实现保留第一行的样式。多行文本的接口 `ansi_escape` 返回 Text，单行接口返回 Line；返回类型本身也在提醒调用方，两种用途有所不同。

最小验证：在 codex-rs 目录执行这个已有测试：

```bash
cargo test -p codex-ansi-escape --lib tests::multiline_warning_contains_counts_and_preserves_the_styled_first_line -- --exact
```

预期恰好选中一个测试。它用红色的 first 作为首行，分别放入短尾部与较长尾部，断言结果仍是带样式的首行，并检查警告中的字节数、行数和固定消息。如果报告零个测试，先检查测试名与当前版本；“零个失败”在这里没有完成验证。

结果解读：测试若通过，支持“单行函数按现有契约工作”，下一步应查看调用方是否应当拆行，或使用多行接口。它并不能证明所有 ANSI 序列都处理正确。即使测试失败，也应先看实际值、期望值和错误位置，避免凭一个症状就重写解析逻辑。

这个案例还说明观察内容的选择。该警告记录输入字节数与行数，而没有把整段原文放入字段。诊断所需的证据可以是结构与计数，不必是完整用户文本。提交问题时，优先构造不包含个人信息的最小输入，并保留能揭示问题的转义序列。

## 日志要回答一个明确问题

当问题只在真实交互中发生，日志才可能提供额外证据。安装文档说明 TUI 默认使用有边界的本地诊断存储；需要明文日志时，要显式指定 log_dir。仅当你原本就准备启动已授权的本地交互会话时，在那个工作目录执行：

```bash
codex -c log_dir=./.codex-log
```

它启动已安装的 Codex，预期为该次运行启用相应日志目录；命令本身不是小包单元测试。随后在另一个终端进入相同工作目录，再执行：

```bash
tail -F ./.codex-log/codex-tui.log
```

预期持续显示日志新增内容；文件尚未创建时，tail 可能等待。先写下你要查的是启动、工具执行还是渲染问题，再寻找相应时间段。`codex exec` 的诊断默认以 error 级别内联输出，不能照搬“所有模式都到同一个 TUI 日志找”的经验。

日志也有边界。没有某条信息，可能是级别、入口或版本不同；有了成功启动的信息，也不证明模型请求完成。连接被拒绝、鉴权失败、断言失败分别指向不同层。记录已观察到的事实，避免把尚未验证的原因写成结论。

## 写一张别人能复查的问题卡

问题卡可依次写：版本与系统、工作目录、完整命令、最小输入、预期值、实际错误、已做的最小验证。需要分享时先删去密钥与私人内容。若暂时没有复现，明确写“尚未复现”，并列出缺少的条件；诚实的不确定比看似肯定的猜测更利于下一步。

最好同时记下一个已排除的方向及排除依据。例如“显式清单路径后，错误从缺少清单变为依赖下载失败”，比“我试过很多次”更具体。如果一次改变了目录、工具版本和依赖配置，即使成功也很难知道原因；先退回可解释的最小改动，再逐项验证。

## 自测与参考答案

题目一：安装工具的命令成功，能否把库测试标为通过？参考答案：不能，需实际运行目标测试并检查选中数量和结果。

题目二：只显示首行一定是缺陷吗？参考答案：先看接口约定；本案例的单行函数就是这样设计的，调用方的预期可能需要调整。

题目三：无法复现时应交付什么？参考答案：交付环境、输入、原始错误、已经排除的假设和仍缺的条件，不要编造通过记录。
